# 기술 발표용 PPT 자동 제작 에이전트 — 통합 설계서

> 이 문서는 Claude Code 구현 시 참조하는 **계획서**입니다. CLAUDE.md, AGENT.md, 스킬 파일의 상세 내용은 포함하지 않으며, 구조·역할·검증 기준까지만 정의합니다.

---

## 1. 작업 컨텍스트 문서

### 1.1 배경
사용자가 보유한 원본 자료(문서, 데이터, 이미지 등)를 매번 수작업으로 슬라이드로 옮기고 디자인을 맞추는 데 시간이 많이 든다. 특히 고객사·외부 청중을 대상으로 하는 발표는 신뢰도와 브랜딩이 중요해 디자인 일관성 유지 부담이 크다.

### 1.2 목적
사용자가 제공한 자료를 분석해 **슬라이드 구성과 핵심 메시지를 설계**하고, **일관된 디자인 규칙**을 적용해 PPT를 제작한다. 빠른 확인·수정을 위해 웹 기반 PPT로 초안을 만들고, 확정 후 `.pptx`로 출력한다.

### 1.3 범위
- 포함: 자료 분석 → 슬라이드 구성 설계 → 웹 PPT 초안 생성 → 피드백 반영 → pptx 출력 → 디자인 규칙 갱신, 필요 시 영어 등 타 언어 슬라이드 생성(번역 포함)
- 제외: 원본 자료 자체의 사실 검증(팩트체크), 발표 리허설/스크립트 작성, 자료 원본 편집

### 1.4 입력
- 원본 자료: 문서(docx/pdf/md 등), 데이터(xlsx/csv), 이미지, 참고 자료(선택)
- 레퍼런스 자료: 참고할 PPT/이미지 (사용자가 파일로 업로드, 복수 가능) — 디자인을 그대로 복제하기 위한 기준이 아니라, 디자인 방향과 우수한 레이아웃·시각화 패턴을 참고하기 위한 자료
- 대상 청중: 고객사/외부 청중(기본값) — 신뢰도·브랜딩 중시, 필요 시 세션마다 변경 가능
- 발표 언어: 기본값 한국어, 필요 시 영어로 번역 생성(원본이 한국어라도 요청 시 지원) — [1] 단계에서 확인
- 발표 조건: 발표 시간 및 목표 슬라이드 수 — [1] 단계에서 명시적으로 확인

### 1.5 출력
- 1차 산출물: 웹 기반 PPT 초안 (HTML/CSS, 브라우저에서 바로 확인 가능)
- 최종 산출물: PowerPoint `.pptx` 파일
- 부산물: 슬라이드 구성안(아웃라인), 갱신된 디자인 규칙 문서
- 선택 산출물: 승인된 웹PPT 버전을 외부와 공유하기 위한 게시 링크(사용자가 명시적으로 요청할 때만 생성 — 1.6 참조)

### 1.6 주요 제약조건
- 청중은 기본적으로 고객사/외부 청중으로 가정 → 신뢰도·브랜딩을 해치는 표현·과도한 세부 데이터 노출 지양
- 레퍼런스 자료는 디자인을 그대로 복제하는 기준이 아니라, 디자인 방향과 우수한 레이아웃·시각화 패턴을 참고하기 위한 자료로 취급한다. 여러 레퍼런스가 제공되면 각 자료의 장점을 분석해 PPT 목적에 적합한 디자인 규칙을 도출한다. 레퍼런스들이 서로 다른 스타일(예: 미니멀 vs 데이터 중심)을 보여 가변 규칙 도출이 충돌하는 경우, 임의로 하나를 선택하지 않고 반드시 사용자에게 선택지를 제시해 확인한다.
- 디자인 규칙은 **고정 규칙**(회사 로고, 브랜드 요소, 지정된 표지 등 반드시 유지해야 하는 요소)과 **가변 규칙**(슬라이드 레이아웃, 차트·표 스타일, 정보 시각화, 강조 방식 등 레퍼런스를 참고해 목적에 맞게 구성 가능한 요소)으로 구분한다. 현재 회사 PPT 디자인 전체가 확정되어 있지 않으므로 규칙은 추가·수정이 가능한 형태로 관리한다. 고정 규칙에 쓰이는 로고 등 브랜드 자산은 프로젝트마다 새로 받지 않고 한 번 등록해 재사용한다.
- 원본 자료의 수치, 실험 결과, 기술적 의미는 임의로 생성·변경·추정하지 않는다. 정확한 확인 또는 해석이 어려운 경우 임의로 판단하지 않고 사용자에게 확인을 요청한다. 차트의 원본 수치를 추출할 수 없는 경우 수치를 눈대중으로 추정해 새 차트를 만들지 않고, 원본 차트를 그대로 활용하거나 사용자에게 원본 데이터를 요청한다. 발표 주장의 근거가 되는 핵심 수치는 확인 전까지 해당 작업을 즉시 중단하고 사용자 응답을 대기하며, 그 외 부가적인 수치는 `[확인필요]` 표시만 남기고 나머지 작업을 계속 진행한다.
- 원본 자료에 상세 데이터 표(수십 행 이상)가 포함된 경우, 슬라이드에는 핵심 행·열만 선별해 표시하고 전체 표는 부록 슬라이드로 별도 처리한다(선별 과정에서 수치 자체는 변경하지 않음).
- 원본 이미지는 그대로 사용하는 것을 원칙으로 하되, 디자인 통일성을 위한 크롭·색보정 등은 허용한다. 내용을 왜곡하는 보정(합성, 수치 변형 등)은 금지한다.
- 원본 자료는 로컬에서만 처리하며, 대화 처리를 위한 LLM 호출 외에는 외부 서비스(클라우드 저장소, 외부 변환 API 등)로 전송하지 않는다. 민감정보 마스킹 등 세부 처리 수준은 구현 단계에서 결정한다. 이 제약은 **미검증 원본 자료**를 대상으로 하며, Human Review를 통과한 완성 웹PPT를 사용자 요청에 따라 공유 링크로 게시하는 것은 예외로 둔다 — 게시는 새 외부 서비스를 추가로 연동하지 않고 기존 LLM 실행 환경(Claude)의 게시 기능만 사용하며, 게시물은 기본 비공개(private)로 생성되어 실제 공유 여부는 사용자가 결정한다. 매 게시 시점마다 어떤 버전을 게시하는지 사용자에게 확인한다.
- 웹PPT를 pptx로 변환할 때 폰트 미보유로 인한 레이아웃 깨짐을 방지하는 것을 우선한다. 임베딩 여부 등 구체적 폰트 정책은 구현 단계에서 결정한다.
- 두 차례의 Human Review(구성 검토, 웹PPT 검토)를 반드시 거친 뒤에만 다음 단계로 진행. 웹PPT 승인 및 pptx 변환이 끝난 뒤에도 재수정 요청이 있으면 pptx를 직접 고치지 않고 웹PPT로 돌아가 수정한 뒤 pptx를 재변환한다.
- 디자인 규칙은 1회성이 아니라 **누적 갱신**되는 자산으로 관리한다(9단계). 단, LLM이 스스로 "일반화 가능한 규칙"이라 판단하더라도 사용자의 명시적 승인 없이는 규칙 문서에 반영하지 않는다.
- 발표 자료(프로젝트)마다 산출물 폴더를 명시적으로 분리하여 과거 발표를 나중에 다시 열어 수정할 수 있어야 한다. 웹PPT 수정 이력은 버전 스냅샷으로 관리하여 이전 버전으로 롤백할 수 있어야 한다.

### 1.7 용어 정의
| 용어 | 정의 |
|---|---|
| 웹 PPT | 브라우저에서 렌더링되는 HTML/CSS 기반 슬라이드 초안 |
| 슬라이드 구성안 | 전체 슬라이드 목록, 각 슬라이드의 핵심 메시지·표현 방식을 정리한 아웃라인 |
| 디자인 규칙 | 색상, 타이포그래피, 레이아웃, 표/차트 스타일 등 반복 적용되는 시각 규칙 세트 (고정 규칙 + 가변 규칙) |
| 고정 규칙 | 회사 로고, 브랜드 요소, 지정된 표지 등 반드시 유지해야 하는 디자인 요소 |
| 가변 규칙 | 슬라이드 레이아웃, 차트·표 스타일, 정보 시각화, 강조 방식 등 레퍼런스를 참고해 목적에 맞게 구성 가능한 디자인 요소 |
| 레퍼런스 자료 | 디자인 방향과 우수한 레이아웃·시각화 패턴을 참고하기 위해 사용자가 제공하는 PPT/이미지. 그대로 복제할 대상이 아님 |
| Human Review | 사용자가 산출물을 검토하고 승인/수정 지시를 내리는 체크포인트 |
| 프로젝트 폴더 | 발표 자료(프로젝트) 단위로 산출물을 분리 보관하는 `/output/{project-name}/` 폴더. 과거 발표를 나중에 다시 열어 수정할 수 있도록 함 |
| 버전 스냅샷 | 웹PPT 수정 이력을 롤백 가능하도록 보관하는 파일 스냅샷(`web_ppt/v1`, `v2` ...). git이 아닌 단순 폴더 복사 방식 |

## 2. 워크플로우 정의

### 2.1 단계별 흐름

```
[1] 자료 입력
     │  - 원본/레퍼런스 자료 수집, 발표 언어·발표 시간·목표 슬라이드 수 확인
     ▼
[2] 자료 분석 (LLM 판단)
     │  - 핵심 내용/데이터/이미지/표/그래프 식별
     ▼
[3] 슬라이드 구성 설계 (LLM 판단)
     │  - 슬라이드 목록, 핵심 메시지, 표현 방식 결정
     ▼
[4] Human Review ①: 구성 검토 ──(수정 요청)──▶ [3]로 재진입
     │ (승인)
     ▼
[5] 웹 PPT 초안 생성 (LLM 판단 + 코드 처리)
     │  - 디자인 규칙 적용, HTML/CSS 슬라이드 렌더링
     ▼
[6] Human Review ②: 웹PPT 검토 ──(수정 요청)──▶ [7]
     │ (승인)                                    │
     │                                            ▼
     │                                   [7] 피드백 반영 수정
     │                                            │
     │◀───────────────────────────────────────────┘
     ▼ (최종 확정)
[8] pptx 변환 및 출력 (코드 처리)
     │
     ▼
[9] 디자인 규칙 갱신 (LLM 판단)
     - 반복 적용 필요 개선사항 → 규칙 문서에 반영
```

### 2.2 분기 조건 / 상태 전이
- **[4]에서 수정 요청**: 어떤 슬라이드/메시지가 문제인지 구조화된 피드백을 받아 [3]으로 되돌아감. 반복 횟수 제한 없음(사용자 승인이 조건).
- **[6]에서 수정 요청**: 내용 문제(메시지·데이터 오류)인지 디자인 문제(레이아웃·스타일)인지 구분하여 각각 다른 처리 경로로 [7]에 전달 — 내용 문제는 슬라이드 구성 재설계 필요 시 [3]까지 소급될 수 있음.
- **[9]는 선택적**: 사용자가 "이 규칙은 앞으로도 적용해줘"라고 명시한 경우에만 규칙 문서에 반영. 1회성 수정은 반영하지 않음. LLM이 자체적으로 일반화 가능하다고 판단한 경우에도 사용자 명시적 승인 없이는 반영하지 않는다.
- **[8] 완료 후 재수정 요청**: pptx 변환·출력까지 끝난 뒤에도 사용자가 재수정을 요청하면 pptx를 직접 편집하지 않고 [7]로 되돌아가 웹PPT를 수정한 뒤 [8]을 다시 수행한다. 이전 웹PPT는 버전 스냅샷으로 보존되어 필요 시 롤백 가능하다.

### 2.3 LLM 판단 영역 vs 코드 처리 영역

| 단계 | LLM 판단 | 코드 처리 |
|---|---|---|
| [2] 자료 분석 | 핵심 메시지·데이터 중요도 판단, 표현 요소(텍스트/차트/표/이미지) 적합성 판단. 수치·실험 결과·기술적 의미는 원본 그대로 반영하며 임의로 생성·추정하지 않음(확인 어려우면 에스컬레이션 대상으로 표시) | 파일 파싱(docx/pdf/xlsx 텍스트·표·이미지 추출) |
| [3] 구성 설계 | 슬라이드 분할, 스토리라인 순서, 슬라이드별 표현 방식 결정. 레퍼런스 스타일이 상충하면 임의로 판단하지 않고 사용자에게 선택지 제시 | 구성안을 구조화된 JSON/MD로 직렬화 |
| [5] 웹PPT 생성 | 고정 규칙은 그대로 준수, 가변 규칙은 레퍼런스에서 파악한 장점을 슬라이드 맥락에 맞게 해석·적용 | HTML/CSS 렌더링, 차트/표 생성 스크립트 실행 |
| [7] 피드백 반영 | 피드백 의도 해석, 수정 범위 판단 | 대상 슬라이드 파일 diff 적용 |
| [8] pptx 변환 | (판단 없음, 예외 상황만 에스컬레이션) | 웹PPT → pptx 변환 스크립트 실행, 무결성 검증 |
| [9] 규칙 갱신 | 이번 피드백이 "일반화 가능한 규칙"인지 "1회성 예외"인지 판단 | 규칙 문서 파일에 append |

### 2.4 단계별 성공 기준 · 검증 방법 · 실패 처리

| 단계 | 성공 기준 | 검증 방법 | 실패 시 처리 |
|---|---|---|---|
| [2] 자료 분석 | 원본 자료의 핵심 요소(주장, 데이터, 시각자료)가 누락·왜곡 없이 추출됨. 수치·실험 결과는 원본과 정확히 일치 | LLM 자기 검증(추출 결과 vs 원본 재대조) | 형식·누락 문제는 자동 재시도 1회. **수치·데이터 확인이 어렵거나 차트 원본 수치를 추출할 수 없는 경우는 재시도 대상이 아니며 에스컬레이션 대상. 발표 주장의 근거가 되는 핵심 수치는 즉시 작업을 중단하고 사용자 확인을 대기하며, 그 외 부가적인 수치는 `[확인필요]` 표시만 남기고 나머지 작업을 계속 진행** |
| [3] 구성 설계 | 슬라이드 구성안이 필수 섹션(제목/핵심메시지/표현방식)을 모두 포함, 청중 유형(고객사)에 맞는 톤 | 스키마 검증(필수 필드) + LLM 자기 검증(톤 적합성) | 형식 오류는 자동 재시도, 톤/논리 문제는 사람 검토([4])로 이관 |
| [4] Human Review ① | 사용자 승인 획득 | 사람 검토 | 수정 요청 시 [3] 재진입, 반복 |
| [5] 웹PPT 생성 | 고정 규칙 준수(로고/브랜드 요소/지정 표지 등), 가변 규칙은 레퍼런스 취지에 맞게 목적에 적합하게 적용, 렌더링 오류 없음, 구성안 내용과 일치, 원본 수치·데이터 왜곡 없음 | 규칙 기반 검증(고정 규칙 체크리스트 대조) + LLM 자기 검증(가변 규칙의 목적 적합성) + 렌더링 오류 로그 확인 | 렌더링 오류는 자동 재시도(최대 2회), 고정 규칙 위반은 재생성, 가변 규칙 적합성 문제는 사람 검토([6])로 이관 |
| [6] Human Review ② | 사용자 승인 획득 | 사람 검토 | 수정 요청 시 [7]로, 필요 시 [3]까지 소급 |
| [8] pptx 변환 | 원본 웹PPT의 디자인·레이아웃을 최대한 유지, 슬라이드 수·내용 일치, PowerPoint에서 텍스트/도형 등이 편집 가능한 상태, 파일 손상 없음 | 스키마 검증(슬라이드 수/요소 수 대조) + 파일 무결성 체크 + 편집 가능 여부 확인 | 자동 재시도(최대 2회) → 지속 실패 시 에스컬레이션 (※ 구체적 변환 방식은 구현 단계에서 결정) |
| [9] 규칙 갱신 | 일반화 가능하다고 LLM이 판단한 규칙도 사용자의 명시적 승인을 받은 뒤에만 반영, 기존 규칙과 충돌 없음 | LLM 자기 검증(일반화 가능성 판단) + 사용자 승인 | 사용자 승인 전에는 반영하지 않고 후보로만 로그에 기록. 판단 불확실 시에도 동일하게 스킵 + 로그(사유 기록) |

### 3.6 서브에이전트 설계

**content-designer**
- 역할: 자료 분석부터 웹PPT 생성/수정까지 일관된 맥락에서 처리
- 트리거: 메인이 [2] 단계 진입 시 호출, [7] 완료까지 유지

- 출력: `slide_outline.md`, `/output/{project-name}/web_ppt/` 파일 경로(버전 스냅샷 포함)
- 참조 스킬: material-analysis, web-ppt-generator

**pptx-converter**
- 역할: 최종 확정 웹PPT를 pptx로 변환
- 트리거: 메인이 [6] 승인 확인 후 [8] 진입 시 호출
- 입력: `/output/{project-name}/web_ppt/` 경로(최신 확정 버전)
- 출력: `/output/{project-name}/final.pptx`
- 참조 스킬: pptx-exporter

### 3.7 데이터 전달 패턴
- 모든 중간 산출물은 `/output/{project-name}/`에 파일로 저장, 에이전트 간에는 **파일 경로만 전달**. 웹PPT 수정 시마다 버전 스냅샷(`web_ppt/vN/`)으로 보존
- 예외: Human Review 시 사용자에게 제시하는 요약(어떤 슬라이드가 어떻게 바뀌었는지 등)은 프롬프트 인라인으로 전달

## 4. 리뷰 대상 사항

### 4.1 확정된 사항 (설계 인터뷰 완료)
아래 항목은 심층 인터뷰를 통해 결정이 완료되어 본문(1~3장)에 반영되었습니다.

- **에이전트 구조**: 2개 서브에이전트(content-designer, pptx-converter) 분리 구조로 확정.
- **청중 유형**: "고객사/외부 청중" 기본값 유지, [1] 단계에서 세션마다 변경 가능.
- **레퍼런스 자료**: 파일 업로드 기준(복수 가능), 복제 기준이 아닌 참고용. 실제 구현 시 첫 사용에서 업로드받은 레퍼런스들을 분석해 가변 규칙 초안을 도출하고 `design-rules.md`(고정/가변 구분)를 만드는 단계가 필요합니다. 고정 규칙(로고·브랜드 요소 등)은 사용자가 별도로 명시하지 않는 한 레퍼런스 분석 대상에서 제외됩니다. 스타일이 상충하는 레퍼런스는 사용자에게 선택지를 제시해 확인합니다.
- **pptx 변환·차트·리뷰 방식·버전 관리·보안·다국어·규칙 갱신 승인** 등 주요 트레이드오프는 1.6, 2장, 3장에 반영된 결정을 따릅니다.

### 4.2 구현 단계에서 결정 필요한 사항
설계 인터뷰에서 원칙은 확정했지만 구체적인 기술 선택은 구현 단계로 남겨둔 항목입니다.

1. **pptx 변환 기술**: "편집 가능한 네이티브 요소로 재구성" 원칙을 만족하는 구체적 변환 라이브러리·도구 선정
2. **차트 라이브러리**: 웹PPT 렌더링과 네이티브 pptx 차트 변환을 함께 지원할 수 있는 도구 선정 (이미지 폴백 경로 포함)
3. **폰트 정책**: 웹 폰트 임베딩 여부, 대체 폰트 매핑 등 레이아웃 안정성 확보를 위한 세부 방식
4. **로컬 처리 원칙의 세부 수준**: 민감정보(PII 등) 마스킹 단계를 워크플로우에 별도로 추가할지 여부
5. **데이터 요약 판단 기준**: 상세 표에서 "핵심 행·열"을 선별하는 구체적 로직/기준
