# Organization Chart --- Curved Leadership

> 임원 프로필과 조직 구성을 하나의 곡선 다이어그램으로 통합하는 조직도
> 레이아웃. 단순 계층 표현보다 핵심 리더를 중심으로 조직이 확장되는
> 구조와 각 책임자의 전문성을 함께 전달할 때 사용한다.

> **Reference-Locked Layout**
> 첨부된 COSOLUS 조직구성 레퍼런스의 배치와 위계를 우선한다.
> 레퍼런스 이미지가 함께 제공된 경우 아래의 좌표·연결 방향·정보 블록
> 분리 규칙은 Soft Rule이 아니라 Hard Rule로 적용한다. 콘텐츠가 달라져도
> 카드형·피라미드형·임의의 대칭형 조직도로 재해석하지 않는다.

------------------------------------------------------------------------

## 1. Layout Intent

이 레이아웃의 핵심은 CEO를 중심으로 주요 임원·조직이 좌우로 펼쳐지는
곡선형 구조이다.

전통적인 피라미드형 조직도보다 다음 내용을 강조하는 경우 우선적으로
사용한다.

-   핵심 경영진 및 주요 책임자
-   각 책임자의 전문 분야
-   담당 조직 및 팀
-   조직 간 관계
-   전문 인력 중심의 기업 역량

곡선은 단순 장식이 아니라 조직 전체를 하나의 시각적 흐름으로 연결하는
핵심 디자인 요소로 사용한다.

------------------------------------------------------------------------

## 2. Core Composition

레퍼런스 고정형의 기본 구조는 다음과 같다.

``` text
 [Management Support] ───●      [CEO Portrait]   [CEO Career]
                                  CEO / Name       Expertise / Career

        Team A ●╲____________________________╱● Team B
                  ╲________●_______________╱
                       Core Organization

   [Left Executive]   [Center Executive]   [Right Executive]
   Profile / Career   Profile / Career     Profile / Career
```

-   CEO Portrait와 직함·이름은 상단 중앙에 배치한다.
-   CEO의 전문 분야·경력은 Portrait 아래에 합치지 않고 우측 독립 텍스트
    블록으로 배치한다.
-   경영지원팀은 좌측 상단의 독립 라벨로 두고 짧은 수평선과 Node로 CEO
    영역에 연결한다.
-   AI혁신팀·기업부설연구소·기술영업팀은 하나의 아래로 처지는 U형 곡선
    위에 배치한다.
-   CSO·CTO·COO Portrait는 해당 팀 Node 바로 아래에 기계적으로 정렬하지
    않는다. 레퍼런스처럼 바깥쪽 또는 왼쪽으로 Offset하여 정보 충돌을 피한다.
-   전체 인상은 카드형이나 피라미드형이 아니라, 상단 CEO와 하단 3개 임원
    정보 블록이 곡선으로 연결되는 부채꼴 구조로 구성한다.

------------------------------------------------------------------------

## 3. Curved Organization Line

곡선형 연결을 기본값으로 사용한다.

### 기본 형태

-   좌측 조직 → 중앙 → 우측 조직을 하나의 연속된 Arc로 연결한다.
-   여러 개의 짧은 곡선을 조합하기보다 하나의 긴 곡선을 우선한다.
-   Arc는 양 끝이 높고 중앙 Node가 낮은 **U형 곡선**이다. SVG 좌표계에서
    중앙 제어점의 Y값은 양 끝점보다 커야 한다. 위로 솟는 ∩형은 금지한다.
-   곡률은 완만하게 유지하며 CEO 이름 아래를 지난다.
-   좌·중·우 세 조직 위치에 모두 Solid Circular Node를 사용한다.
-   화살표는 사용하지 않는다.
-   곡선은 위계선을 직접적으로 표현하기보다
    `핵심 리더를 중심으로 조직이 펼쳐지는 관계`를 표현하는 시각적 장치로
    사용한다.

### SVG 기준 예시

본문 좌표계가 `1152 × 529`일 때 다음 값을 기준으로 시작한다.

``` svg
<path d="M 220 110 Q 576 235 930 110" />
<circle cx="220" cy="110" r="8" />
<circle cx="576" cy="172" r="8" />
<circle cx="930" cy="110" r="8" />
```

- 실제 중앙 Node는 Quadratic Curve 위의 중간점에 맞춘다.
- 선 두께는 1.25~1.75px, Node 지름은 14~18px를 사용한다.
- `M 220 210 Q 576 100 930 210`처럼 중앙이 위로 올라가는 경로는 금지한다.

## 4. Straight Line Exception

직선은 기본 디자인이 아니라 예외 처리로 사용한다.

다음 상황에서는 부분적으로 직선을 허용한다.

-   텍스트 또는 Portrait로 인해 곡선이 지나갈 물리적 공간이 부족한 경우
-   두 Node 사이의 거리가 매우 짧아 곡률 표현이 의미 없는 경우
-   곡선 사용 시 Portrait, 본문 또는 다른 Connector와 충돌하는 경우
-   동일한 수평 또는 수직 관계를 직선으로 표현하는 것이 더 자연스러운
    경우

가능한 경우 전체 조직도의 핵심 연결 구조는 곡선으로 유지한다.

곡선을 유지하기 위해 본문 크기를 과도하게 축소하지 않는다.

------------------------------------------------------------------------

## 5. Node System

조직의 성격에 따라 Node 표현 방식을 구분한다.

  Node Type                    Visual Treatment
  ---------------------------- -----------------------
  CEO / Executive              원형 Portrait
  Team / Department            Solid Dot + Team Name
  Research Center / Division   Text Label
  Sub-team                     Dot Bullet + Text

동일한 Level의 Node는 동일한 시각적 Weight를 유지한다.

------------------------------------------------------------------------

## 6. Portrait System

임원 또는 주요 책임자는 원형 Portrait를 기본으로 사용한다.

### 기본 원칙

-   동일한 원형 Mask 사용
-   동일하거나 유사한 배경 톤 적용
-   가능하면 인물 사진의 채도 및 명암 수준 통일
-   동일 Level 인물은 동일 크기 유지

### Visual Priority

CEO \> 주요 임원 \> 팀 책임자

CEO는 조직도의 시각적 Anchor 역할을 하므로 가장 높은 Priority를
부여한다.

단, 배치 공간 확보를 위해 동일 Level 인물의 크기를 임의로 크게 차등
적용하지 않는다.

### 사진 미확보 시 Placeholder

실제 인물 사진이 아직 제공되지 않은 경우, 가짜 사진을 임의로 생성하거나
이니셜 아바타로 대체하지 않는다.

-   점선(Dashed) 테두리의 원형 Placeholder를 사용한다.
-   내부에는 간단한 인물 실루엣 아이콘만 배치한다(이니셜 텍스트는 실제
    사진처럼 오인될 수 있어 사용하지 않는다).
-   배경은 Neutral/Mist 계열 톤을 사용한다.
-   실제 사진이 제공되면 Placeholder를 그대로 대체하되, 원형 Mask·크기
    규칙(동일 Level 동일 크기)은 유지한다.

## 7. Executive Information Structure

인물 정보는 다음 순서를 기본으로 한다.

1.  Position
2.  Name
3.  Expertise / Main Role
4.  Career
5.  Assigned Team

예시:

``` text
CTO
홍길동

유기합성

▪ 2021.08  ○○대학교 화학 박사
▪ 2022.03~ ○○기업 연구소장
▪ 논문 18편 / 특허 7편

● 개발1팀 (6명)
● 개발2팀 (4명)
```

모든 정보를 반드시 사용할 필요는 없다.

콘텐츠 중요도에 따라 Career 또는 Team Information을 축약할 수 있다.

------------------------------------------------------------------------

## 8. Information Hierarchy

권장 시각적 우선순위:

1.  Portrait
2.  Position
3.  Name
4.  Team / Organization Name
5.  Expertise
6.  Career
7.  Sub-team Information

팀명 및 조직명은 Connector와 연계하여 관계가 즉시 인식되도록 배치한다.

경력 정보는 조직도 자체보다 높은 시각적 Weight를 갖지 않도록 한다.

------------------------------------------------------------------------

## 9. Team Label

Team Node는 다음 구조를 기본으로 한다.

`● 팀명 (N명)`

-   Solid Dot + Team Name 조합 사용
-   인원 정보가 제공된 경우 괄호로 병기 가능
-   팀명은 한 줄 표현을 우선한다.
-   지나치게 긴 팀명은 의미를 훼손하지 않는 범위에서 축약 가능

Sub-team은 담당 임원 정보 하단에 Bullet List 형태로 배치할 수 있다.

### 배치 위치

-   팀/조직명 라벨은 곡선 위 해당 Node 지점(위쪽)에 배치하는 것을
    기본으로 하며, 인물의 Portrait·Position·Name 정보 블록(아래쪽)과
    시각적으로 분리한다.
-   이렇게 분리하면 "이 Node가 어떤 조직인가"와 "이 조직을 누가
    이끄는가"가 한눈에 구분된다.
-   Node 라벨과 인물 정보 블록을 하나로 합쳐 인물 블록 안에 조직명을
    반복 표기하지 않는다(단, 인물 정보의 Assigned Team 항목에 인원수를
    함께 표기하는 것은 허용한다).
-   조직 라벨과 인물 Portrait의 X좌표는 반드시 같을 필요가 없다. 레퍼런스
    고정형에서는 관계를 나타내는 Node와 인물 정보 블록을 분리하여 충돌을
    방지한다.

## 10. Placement Logic

### CEO

-   상단 중앙 배치
-   전체 조직도의 Visual Anchor 역할
-   Portrait 아래에는 `CEO → 이름`만 배치한다.
-   전문 분야와 경력은 CEO 우측의 Left Align 텍스트 블록으로 분리한다.
-   CEO 정보가 중앙 곡선이나 기업부설연구소 라벨을 침범하지 않도록 한다.

### Other Executives

-   CSO는 좌측 하단, CTO는 중앙보다 약간 왼쪽의 최하단, COO는 우측 하단에
    분산한다.
-   화면 전체에 균형 있게 배치
-   완전한 좌우 대칭보다 콘텐츠 밀도에 따른 시각적 균형을 우선
-   CTO Portrait는 좌·우 임원 Portrait보다 50~90px 아래에 두어 중앙 조직
    라벨과 경력 블록을 위한 공간을 확보한다.
-   좌·중·우 정보 영역 사이에는 매우 얇은 세로 구분선을 사용할 수 있다.
    구분선은 곡선과 연결하지 않으며 정보 블록 경계만 보조한다.

### Text Alignment

-   좌측 인물: Left Align 우선
-   중앙 인물: Center 또는 Left Align 선택 가능
-   우측 인물: 화면 바깥으로 텍스트가 밀리지 않는 방향으로 정렬

정렬 방식 자체보다 Portrait와 정보 블록 간 관계의 명확성을 우선한다.

## 11. Content Density Adaptation

정보량 증가 시 다음 순서로 대응한다.

1.  중요도가 낮은 Career 정보 축약
2.  세부 Team 정보 축약
3.  Portrait 및 Node 간 간격 조정
4.  Portrait 크기 소폭 조정
5.  단일 Arc 내 Node 재배치
6.  충분한 가독성이 확보되는 경우 2단 Arc 구조 검토
7.  곡선형 구조로 가독성 확보가 불가능한 경우 다른 조직도 레이아웃 검토

글자 크기를 과도하게 축소하여 레이아웃을 억지로 유지하지 않는다.

------------------------------------------------------------------------

## 12. Multi-Arc Expansion

기본형은 Single Arc 구조이다.

조직 또는 인물 수가 증가할 경우 필요에 따라 두 번째 Arc를 추가할 수
있다.

``` text
                   CEO
                    │

       ●──────── Curved Arc ────────●
             Major Organizations

          ●──── Second Arc ────●
               Sub Organizations
```

단, Arc 추가는 자동적으로 적용하지 않는다.

다음 조건을 만족할 때만 사용한다.

-   조직 간 관계가 명확히 2개 Level로 구분되는 경우
-   두 번째 Arc를 사용해도 충분한 여백이 확보되는 경우
-   Connector가 서로 교차하지 않는 경우
-   정보 가독성이 Single Arc보다 실제로 개선되는 경우

> **16장과의 구분**: 이 12장은 CEO를 중심으로 한 하나의 Arc 구조 "안에서" 팀/하위조직
> 레벨의 정보량이 늘어나 Arc를 하나 더 추가하는 경우(모든 Node가 여전히 CEO 직속
> 위계 안에서 표현됨)를 다룬다. 반면 특정 비-CEO 리더 Node 자신이 또 다른 리더들의
> 상위 허브가 되어 실제로 다른 위계 단(Level)을 구성하는 경우는 16장
> "Two-Level Executive Hub"를 참고한다. 두 상황을 혼동해 12장의 Arc 추가 조건만으로
> 16장이 다루는 구조를 판단하지 않는다.

## 13. Visual Simplicity

곡선 조직도 자체가 강한 Visual Element이므로 추가적인 장식을 최소화한다.

Avoid:

-   과도한 Box 사용
-   조직별 배경 Panel 남용
-   Connector Arrow
-   복잡한 S-Curve
-   Connector 교차
-   불필요한 Shadow
-   Gradient Connector
-   지나치게 많은 색상
-   조직별 임의 색상 구분

Portrait + Curve + Node + Typography만으로 조직 관계를 전달하는 것을
우선한다.

------------------------------------------------------------------------

## 14. Soft Rule

조직 관계가 비교적 단순하고 핵심 임원의 전문성과 담당 조직을 함께
보여주는 경우 Curved Organization Layout을 우선적인 시각화 후보로
검토한다.

곡선의 정확한 좌표, Portrait 위치 및 각 정보 블록의 크기는 콘텐츠 분량에
따라 조정할 수 있다. 단, 레퍼런스 이미지가 제공된 경우에는 16장의 좌표
가이드를 우선 적용하며 조정 폭은 각 축 ±3% 이내로 제한한다.

완전한 대칭보다 시각적 균형과 정보 가독성을 우선한다.

콘텐츠가 증가하더라도 곡선형 레이아웃의 핵심 특징인 다음 요소는 최대한
유지한다.

-   중앙 핵심 리더
-   좌우로 확산되는 조직 구조
-   완만한 Arc
-   Solid Node
-   원형 Portrait
-   최소화된 Connector

------------------------------------------------------------------------

## 15. Layout Identity

이 레이아웃의 핵심 디자인 Identity는 다음과 같다.

`Central Leader + Circular Portrait + Single Arc + Solid Nodes + Distributed Leadership`

레이아웃을 변형하더라도 위 조합이 유지되어 원본 디자인의 시각적 정체성이
사라지지 않도록 한다.

곡선은 기본 디자인 언어이며, 직선은 콘텐츠 또는 공간 제약을 해결하기
위한 보조 수단으로만 사용한다.

자체 재배치를 하지 않는다.

메인 곡선(U형 Arc)은 좌측 Node(284, 303.8) → Hub Node(653.1, 379.2, 곡선의
최저점) → 우측 Node(990.1, 303.8) 3점을 지나는 하나의 완만한 곡선으로 재현한다
(원본은 PowerPoint 네이티브 Arc 도형이지만, 웹/SVG 구현에서는 이 3점을 지나는
2차 Bezier로 근사하면 시각적으로 동일하다).

**2차 Bezier 제어점 계산법** — 좌측점 `(x1,y1)`, 우측점 `(x2,y2)`, 곡선이
반드시 지나야 하는 중앙 최저점 `(xm,ym)`이 주어졌을 때, 제어점
`(cx,cy) = (2·xm − (x1+x2)/2, 2·ym − (y1+y2)/2)`. 이 슬라이드의 값(284,303.8),
(990.1,303.8), 중앙(653.1,379.2)을 대입하면 제어점은 (669.15, 454.6)이며,
SVG path는 `M284,303.8 Q669.15,454.6 990.1,303.8`이다. 좌우 Node 좌표가
바뀌어도 이 공식으로 항상 정확히 중앙점을 지나는 곡선을 얻을 수 있다.

### 16.1.2 구현 메모 (Implementation Notes)

- **좌표계**: 이 장의 모든 X/Y는 슬라이드 전체 기준 절대좌표(1280×720)다.
  기존 web_ppt 관례처럼 `.slide-body`(좌우 64px, 상단 135px, 하단 56px 여백)
  안에 `.org-field`를 중첩시키고 그 안에서 다시 0~1152×0~529 좌표를 쓰는
  방식이 아니다. 구현 시 `.org-field { position:absolute; inset:0; }`로
  `.slide` 전체를 덮고, 표의 좌표를 변환 없이 그대로 `left`/`top`에 쓴다.
  헤더·구분선·타이틀블록(§Hard Rule 공통 헤더)은 그대로 두되 z-index로
  `.org-field` 콘텐츠 위에 오도록 한다(포트레이트가 헤더 영역까지 올라오지
  않으므로 실제 충돌은 없다).
- **Portrait 크롭 크기**: 링(그라디언트 배경) 지름은 CEO 153.5px·임원
  153.6px로 통일하지만, 그 안의 실제 사진은 완전한 정사각형이 아니어도
  된다(원본 인물사진 종횡비를 유지) — CEO 140.2×140.2, CTO 141.4×135.1,
  CSO 130.4×134.9, COO 146.5×141.9. 사진은 링 중앙에 배치하고
  `object-fit:cover`+원형 클리핑을 적용한다.
- **세부팀/설명줄 Bullet Dot**: 곡선 위 주요 Node(경영지원팀·Hub·좌우
  Arc-end)와 달리, 세부팀 리스트(개발1/2/3팀·생산1팀)와 하단 설명줄의
  작은 점은 SVG Node가 아니라 텍스트 왼쪽에 붙는 별도의 작은 원(지름
  ~10.4px)이다. 텍스트 시작 X 기준 약 -17~-19px 위치(줄 폭에 따라 미세
  조정, 이 레퍼런스에서는 -19.1/-19.2/-16.8px)에 둔다. 같은 위치에 SVG
  Node와 텍스트 dot을 동시에 그리면 이중 원이 겹쳐 물방울/찌그러진
  모양으로 보이는 렌더링 결함이 생기므로 반드시 한쪽만 사용한다.
- **곡선 SVG는 슬라이드 전체를 덮지 않는다**: `.org-field`는 `.slide` 전체를
  덮어도 되지만, 그 안의 `<svg>`(메인 곡선 담당)는 `inset:0`으로 슬라이드
  전체 크기를 차지하게 두면 안 된다. `pptx-exporter`는 CSS `z-index`를 보지
  않고 DOM 순서로만 도형을 쌓는데, 헤더(로고·구분선·타이틀·페이지번호)보다
  이 svg가 DOM에서 뒤에 오기 때문에, svg가 슬라이드 전체 크기(헤더 영역
  포함)로 캡처되면 그 캡처 PNG가 헤더 위에 얹혀 로고·타이틀이 통째로
  가려진다(브라우저에서는 헤더 z-index:3 덕분에 정상으로 보여서 웹 미리보기
  단계에서는 이 문제가 드러나지 않는다 — 반드시 pptx로 변환한 뒤 상단 헤더가
  보이는지 확인한다). 해결: `<svg>`의 `viewBox`와 CSS `left/top/width/height`를
  실제 곡선이 그려지는 좌표 범위(이 레퍼런스 기준 x:260~1020, y:180~405)로
  좁힌다 — viewBox 원점을 옮겨도(`viewBox="260 180 760 225"`) 내부 `<path>`/
  `<circle>`의 절대좌표(예: `cx="284"`)는 그대로 쓸 수 있다.
- **pptx 변환 전제조건**: `<img>`를 원형으로 자르는 CSS(`border-radius:50%`)가
  부모 div에 걸려 있어도 `.claude/skills/pptx-exporter/scripts/export_pptx.py`
  가 이를 감지해 PowerPoint 도형 geometry를 `ellipse`로 바꿔주는 로직이
  있어야 실제 pptx에서도 원형 사진으로 보인다(2026-08-21 이 스크립트에
  해당 로직 추가 완료 — `add_picture_exact`/`set_picture_geometry_ellipse`,
  이미지 자신 또는 부모의 `borderRadius`를 모두 확인). 이 로직이 없는 옛
  버전 스크립트로 변환하면 사진이 사각형으로 나온다.
- **경력 블록 배치 원칙(일반화)**: 이름(Position+Name)은 항상 Portrait
  바로 아래 중앙 정렬로 고정한다. 전문분야 헤딩+경력 Bullet은 이름과 별도
  블록으로 분리해 Portrait의 좌/우 한쪽으로 오프셋한다 — 어느 쪽으로
  오프셋할지는 화면상 위치에 따른다(맨 왼쪽 임원은 왼쪽, 맨 오른쪽 임원은
  안쪽/왼쪽, CEO와 중앙 인접 임원은 오른쪽). 오프셋 블록의 X 범위가 이름

### 16.3 Mandatory Visual Rules

- Portrait는 모두 원형이며 동일한 Teal 계열 그라디언트 배경(`#C1E9E8→#339387`,

  153.6px로 사실상 동일하다(설계서 §6의 "5~10% 이내" 규정과 일치).
- 메인 곡선은 반드시 아래로 처지는 U형이다.
- 곡선 위 라벨은 좌→중→우 순서를 유지하며, 좌/우 라벨은 각 Node의 바깥쪽
  (중앙에서 먼 쪽)에, 중앙(Hub) 라벨은 Node 바로 아래에 배치한다.
- 경영지원팀은 메인 곡선에 합치지 않고 상단 좌측의 별도 수평(0°) 연결선으로
  둔다.
- 조직별 카드, 배경 패널, 둥근 사각형, 그림자, 화살표를 사용하지 않는다.
- 좌·중·우 정보 블록 사이 세로 구분선은 허용하되 Portrait나 곡선을
  관통하지 않는다.

### 16.4 Validation Checklist

생성 후 다음을 이미지 기준으로 검증한다.

1. 메인 곡선이 U형인가? 위로 솟는 ∩형이면 실패이다.
2. CEO 경력이 Portrait 아래가 아니라 우측에 있는가?
3. CTO가 중앙 Node 바로 아래가 아니라 왼쪽 아래(y+90px 내외)에 배치되어
   있는가?
4. CSO와 COO가 곡선 양 끝 바깥쪽으로 펼쳐져 있는가?
5. 경영지원팀이 별도 수평 연결선으로 유지되는가?
6. 3개 조직 라벨과 3개 임원 정보 블록이 다른 역할로 분리되어 있는가?
7. Hub(기업부설연구소) 라벨이 CEO→곡선 연결선의 Node 바로 아래에 있는가
   (Node 위쪽이 아님)?
8. Portrait가 실제로 원형으로 잘려 보이는가(사각형으로 삽입되지 않았는가)?
9. 좌/우로 오프셋된 경력 블록이 이름 텍스트와 겹치지 않는가(겹치면 16.1
   보정 규칙대로 경력 블록을 이름 아래로 내렸는가)?
10. 세부팀/설명줄의 작은 점이 이중으로 겹쳐 물방울처럼 보이지 않는가?
11. **pptx로 변환한 결과물을 열어서(웹 미리보기만으로는 발견 안 됨) 로고·
    "COMPANY"·타이틀·페이지번호가 실제로 보이는가**(곡선 svg가 헤더 영역까지
    덮으면 DOM 순서상 헤더 위에 얹혀 가려진다 — 16.1.2 참고)?
12. 카드형·피라미드형 조직도로 재해석되지 않았는가?

하나라도 실패하면 단순 미관 조정으로 처리하지 말고 Layout Identity 위반으로
판정하여 다시 생성한다.

## Appendix. Two-Level Executive Hub (이번 레퍼런스에는 적용 금지)

아래 변형은 실제 원본 자료가 별도의 2단 위계를 명시한 다른 조직도에만
사용한다. COSOLUS 레퍼런스에서는 `기업부설연구소`를 CTO 상위 허브로
재해석하지 않으며, 이 Appendix보다 16장의 단일 U형 구조가 우선한다.

기본형(2~14장)은 CEO 한 명이 조직 전체의 유일한 Hub 역할을 하는 구조를
전제한다. 그러나 실제 조직에서는 CEO가 아닌 특정 리더 — 예: 기업부설연구소를
이끄는 CTO처럼, 개인 임원 직함과 별도 조직(연구소/본부/사업부 등)의 대표를
동시에 겸하는 인물 — 자신이 또 다른 실행 리더들의 상위 허브가 되는 경우가
있다. 12장 "Multi-Arc Expansion"은 이런 경우를 다루지 않는다(12장은 동일한
CEO 직속 위계 안에서 팀/하위조직 정보량이 늘어난 상황이다). 이 Appendix는 실제로
서로 다른 위계 단(Level)이 존재하는 경우를 다룬다.

### A.1 언제 사용하는가

다음 조건을 모두 만족할 때만 이 구조를 검토한다.

-   원본 자료(조직도 등)가 특정 비-CEO 리더 Node 아래에 다시 갈라지는 하위
    리더 Node들을 명시적으로 표시하고 있는 경우
-   그 비-CEO 리더가 개인 임원 직함과 별도로 조직/연구소/본부 단위를
    대표하는 것으로 확인되는 경우
-   이 관계를 단일 Arc(2장 기본형)나 두 번째 Arc(12장)로 표현하면 실제
    위계가 왜곡되거나("허브가 CEO와 동일 레벨의 임원처럼 보임"), 반대로
    허브에 속하지 않는 다른 임원과 착각을 일으킬 위험이 있는 경우

이 조건에 해당하지 않는 한, 기본형 Single Arc(2~14장)를 우선 검토한다 —
모든 조직도에 이 구조를 기계적으로 적용하지 않는다.

### A.2 구조

``` text
                         [CEO Portrait]
                         CEO / Name

                              │
                    [Hub Executive Portrait]
                    Position / Name / Career
                    Sub-team Bullet List (자신의 산하 팀)

          ╭──────────────────────────────╮
    [Leader Portrait]                [Leader Portrait]
    Position / Name                  Position / Name
    Sub-team Label                   Sub-team Label
```

-   CEO의 1차 자녀는 여전히 CEO 바로 아래 직접 연결된 Node들이다(Hub
    Executive를 포함해 다른 팀/조직 Node가 있으면 함께 표시).
    CEO 직속의 다른 팀(예: 경영지원팀)이 있다면 Hub 위계와 무관하게 CEO에서
    별도로 직접 연결한다 — Hub의 하위 트리에 억지로 편입시키지 않는다.
-   Hub Executive Node는 5장 Node System 기준 "CEO/Executive: 원형
    Portrait"로 표현하되, 자신이 대표하는 조직명이 있으면 9장 Team Label
    배치 원칙에 따라 Portrait 위(곡선 위 Node 지점)에 조직명 Text Label을
    추가한다(Research Center/Division 유형이면 Dot 없이 Text Label만).
-   Hub Executive 자신의 산하 팀(개발팀 등)은 7장 Executive Information
    Structure의 Assigned Team 규칙대로 Hub 자신의 정보 블록 하단에 유지한다
    — 아래 2차 리더 Node와 혼동하지 않는다.
-   Hub 아래 갈라지는 2차 리더 Node들은 동일하게 5장 Node System의
    "CEO/Executive" 유형(원형 Portrait)을 사용하되, 6장 Portrait System의
    Visual Priority(CEO > 주요 임원 > 팀 책임자) 순서에 맞춰 CEO보다 작고,
    가능하면 Hub Executive보다도 한 단계 작은 크기를 사용해 이들이 CEO
    직속이 아니라 Hub 아래에 있다는 것을 크기로도 보조 전달한다(단, 2차
    리더끼리는 서로 동일 Level이므로 동일 크기를 유지한다 — 5장 규칙과
    동일).
-   2차 리더가 자신의 이름으로 된 하위 팀(예: 위 예시의 AI혁신팀,
    기술영업팀)을 이끄는 경우, 그 팀을 별도 분기 Node로 만들지 않는다.
    9장 Team Label 규칙대로 해당 2차 리더의 정보 블록 하단에 Sub-team
    Bullet 항목으로만 표기한다 — "이 사람이 이끄는 팀"과 "이 사람 자체를
    가리키는 조직 허브"를 같은 시각적 무게의 Node로 동시에 그리면 위계가
    한 단계 더 있는 것처럼 착시를 일으킨다(이번 개정의 배경이 된 실수).

### A.3 Connector

-   CEO → Hub Executive 연결은 3장/4장의 곡선 우선 원칙을 그대로 따르되,
    두 Node가 상하로 가깝고 중앙에 정렬되어 있다면 4장의 Straight Line
    Exception("동일한 수직 관계를 직선으로 표현하는 것이 더 자연스러운
    경우")에 해당하는 것이 일반적이다 — 짧은 직선 하나로 표현한다.
-   Hub Executive → 2차 리더 연결은 3장의 곡선을 기본으로 하되, 다음을
    추가로 지킨다(이 Appendix의 핵심 원칙):
    -   **CEO의 1차 연결(Arc 또는 직선)보다 시각적으로 더 종속적으로
        보여야 한다.** 구체적으로: (1) 곡선의 수직 진폭(높이 차이)을 CEO
        1차 구조보다 작게 유지하고, (2) 화면상 더 아래쪽(낮은 위치)에
        위치시키며, (3) 필요하면 Stroke 두께를 CEO 1차 연결보다 얇게, 색은
        13장이 금지하는 새 임의 색상이 아니라 이미 정의된 Design System
        Brand Color 팔레트 안의 보조 색상(Secondary 등)으로 낮춰 1차
        연결과 구분한다.
    -   Solid Node(3장), 화살표 금지(3장/13장) 등 기존 Connector 규칙은
        동일하게 적용한다.
    -   이렇게 구분해도 전체 구도에서 **CEO가 여전히 최상위 Visual
        Anchor로 읽혀야 한다**(6장 Visual Priority 원칙) — Hub Executive나
        2차 리더 어느 쪽도 CEO보다 크거나 시각적으로 무거워서는 안 된다.

### A.4 Do Not

-   Hub가 대표하는 조직명과, 그 아래 2차 리더가 이끄는 팀명을 같은 층위의
    분기 Node로 동시에 그리지 않는다(예: "허브 조직명"과 "2차 리더의 팀명"을
    나란히 같은 크기의 분기점으로 배치 — 실제로는 후자가 전자보다 한 단
    아래에 있다).
-   Hub Executive와 2차 리더의 Portrait 크기를 동일하게 두어 위계 차이를
    지우지 않는다(6장 Visual Priority 위반).
-   이 구조를 CEO 직속 리더가 단순히 여러 명(3명 이상)인 일반적인 경우에
    기본값으로 적용하지 않는다 — 그 경우는 2장 기본형이나 12장을 우선
    검토한다.
